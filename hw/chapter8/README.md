## 3. 退化为 RR

设置 -n 1，只保留一个队列，用 -q 指定时间片；保持默认 I/O 队尾入队，不启用 -I。

    python3 ext/ostep-homework/cpu-sched-mlfq/mlfq.py -n 1 -q 3 -l 0,8,0:0,8,0:0,8,0 -c

结果：0、1、2 各运行 3 ms，重复一轮，最后各运行 2 ms。优先级始终相同，逐毫秒轨迹与 RR 推算一致。

## 4. 旧规则下占用 99% CPU

    python3 ext/ostep-homework/cpu-sched-mlfq/mlfq.py -n 2 -q 100 -i 1 -I -l 0,2000,0:100,990,99 -S -c

Job 0 先运行一个 100 ms 时间片后降级；Job 1 在 100 ms 到达，每运行 99 ms 就发起耗时 1 ms 的 I/O。-S 清除已经消耗的配额，-I 让它回到队首，-B 默认为 0。

在 [100,1100) 中 Job 1 获得 990 ms、Job 0 获得 10 ms，份额恰为 99%。Job 1 最后一次执行完成后不再发起 I/O，区间末尾的 1 ms 由 Job 0 使用。

删除 -S 后，同区间 Job 1 份额为 50.0%。累计记账保留每级已经使用的 CPU 时间，任务仍会降级，所以旧规则的优势不能持续。

## 5. 多久提升一次优先级

若每次提升能确保长作业运行完整的最高级时间片 10 ms，则平均份额至少为 10/B。要求 10/B >= 0.05，得 B <= 200 ms，所以可设置 -B 200。

    python3 ext/ostep-homework/cpu-sched-mlfq/mlfq.py -q 10 -i 1 -S -B 200 -l 0,1000,0:100,1000,1:100,1000,1 -c

本验证关闭 -I，Job 0 在 [200,400) 实际运行 10 ms。

额外保留启用 -I 的反例，见 q5-boost200-with-I.txt；此时提升后的长作业仍可能被队首插入的 I/O 作业挤占服务。

边界：200 ms 的答案依赖“每周期至少服务 10 ms”的假设，仅设置 -B 不能对任意竞争负载保证每个任务都占 5%。例如 21 个持续就绪任务各得 5% 将需要 105% CPU。竞争者数量、队列顺序和 -I 插队都会影响服务延迟；本实验不构成任意负载的普遍保证。

## 6. I/O 完成后回队尾或队首

    python3 ext/ostep-homework/cpu-sched-mlfq/mlfq.py -n 1 -q 10 -i 2 -l 0,30,3:0,30,0 -c

    python3 ext/ostep-homework/cpu-sched-mlfq/mlfq.py -n 1 -q 10 -i 2 -l 0,30,3:0,30,0 -I -c

Job 0 在 [0,3) 运行后 I/O，在 5 ms 完成。默认回队尾，Job 1 从 3 ms 运行至 13 ms 后 Job 0 才能恢复；启用 -I 后，Job 0 在 5 ms 直接回队首并运行，能够打断同级 Job 1 尚未用完的时间片。-I 不提高任务所属队列的优先级。

| 模式 | 完成时刻 (ms) |
| --- | --- |
| 默认队尾 | {1: 39, 0: 72} |
| -I 队首 | {0: 56, 1: 60} |

队首插入通常改善 I/O 任务恢复响应，但可能增加同级 CPU 任务等待，不能断言所有作业周转时间都会改善。
